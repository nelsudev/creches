# Issue decision automation design

## Objective

Create one review issue per creche and a reusable GitHub Issue Form for future entries. A repository collaborator decides by commenting exactly `aceite` or `rejeitado`. GitHub Actions applies the matching decision label, updates the repository Markdown, commits to `main`, comments with the result, and closes the issue.

This workflow records a review decision. It does not simulate contact with a creche, prove that a vacancy exists, or replace the human-only phases documented in `AGENTS.md`.

## Decision workflow

Each review issue starts with the label `decisao:pendente`.

1. An authorized collaborator comments `aceite` or `rejeitado` (case-insensitive, surrounding whitespace ignored).
2. The workflow checks `author_association`; only `OWNER`, `MEMBER`, or `COLLABORATOR` may decide.
3. The workflow serializes repository-writing jobs to avoid two decisions pushing concurrently.
4. It validates the issue metadata, target path, proposed Markdown, and index row.
5. It applies one terminal label:
   - `decisao:aceite`
   - `decisao:rejeitado`
   - `decisao:erro` when validation or writing fails
6. On success it commits and pushes the Markdown change, comments with the commit identifier, and closes the issue.
7. On failure it leaves the issue open and comments with a concise, actionable error.

Repeated commands are idempotent. If an issue already has a terminal decision label, later comments do not create another commit.

## Issue representation

The repository will contain `.github/ISSUE_TEMPLATE/revisao-creche.yml`. It collects:

- creche name;
- zone;
- canonical slug;
- target ficha path;
- proposed complete ficha Markdown;
- proposed index row;
- evidence/notes for the reviewer.

The issue body uses exact, machine-readable headings for:

- `target_path`;
- the proposed ficha Markdown;
- the proposed index row.

The two Markdown payloads are fenced code blocks generated by Issue Form textareas with `render: markdown`. Exact headings plus fenced blocks make parsing deterministic and avoid inferring paths from titles or human prose.

For the current repository, a creation script reads every `fichas/<zona>/*.md` and its matching row in `creches.md`, then opens one pre-filled review issue per canonical ficha using the same headings and fenced blocks. It adds the zone label and `decisao:pendente`. Creation is idempotent: the canonical target path is the stable key used to search existing review issues before creating another.

There are currently 34 canonical fichas:

- 5 in Trofa;
- 15 in Matosinhos;
- 14 in Porto/Ramalde.

## Accepted decision

For `aceite`, the processor:

1. validates that `target_path` matches `fichas/(trofa|matosinhos|porto-ramalde)/<slug>.md`;
2. rejects path traversal, absolute paths, non-Markdown targets, and targets outside `fichas/`;
3. validates that the proposed Markdown has a title, `Fontes consultadas`, and no empty machine metadata;
4. validates that the proposed index row links to the same target path;
5. writes the proposed ficha Markdown;
6. adds or updates `**Estado da decisão:** Aceite (AAAA-MM-DD, issue #N)`;
7. replaces the matching index row, or inserts it in the correct zone table when creating a new entry;
8. records `Aceite em AAAA-MM-DD` in the row notes without discarding existing notes.

The commit message is `feat(decision): accept <slug> (#N)`.

## Rejected decision

For `rejeitado`, the processor preserves the researched data and records the decision:

1. adds or updates `**Estado da decisão:** Rejeitado (AAAA-MM-DD, issue #N)` in the existing ficha;
2. updates the matching index row notes with `Rejeitado em AAAA-MM-DD`;
3. does not import other edited proposal fields from the issue.

The commit message is `docs(decision): reject <slug> (#N)`.

This makes rejection visible in both the detailed ficha and the index while keeping the evidence recoverable.

## Components

### Labels

- `decisao:pendente`
- `decisao:aceite`
- `decisao:rejeitado`
- `decisao:erro`

The setup script creates missing labels with stable colors and descriptions.

### Scripts

- `scripts/decision/parse-issue.mjs`: extract and validate marked fields.
- `scripts/decision/update-markdown.mjs`: apply accepted/rejected state to ficha and index.
- `scripts/decision/process.mjs`: fetch issue data, orchestrate validation, write files, and return structured output.
- `scripts/decision/create-review-issues.mjs`: create labels and the 34 pre-filled review issues without duplicates.

Scripts use Node.js built-ins. GitHub API requests use the workflow token; local bulk creation uses authenticated `gh`.

### Workflows

- `.github/workflows/decision.yml`: triggered by `issue_comment.created`; validates authority and command, checks out `main`, runs the processor, commits, pushes, labels, comments, and closes.
- `.github/workflows/validate-review-issue.yml`: triggered when a review issue is opened or edited; validates its markers and applies `decisao:pendente` or `decisao:erro`.

Permissions are limited to `contents: write` and `issues: write`. Other event types and comments are ignored.

## Error handling

The workflow must not commit when:

- the commenter is unauthorized;
- the command is not exactly `aceite` or `rejeitado`;
- the issue is not a review issue;
- the target path is unsafe;
- required headings or fenced payloads are missing or duplicated;
- the index row points to another ficha;
- the issue already has a terminal decision.

Validation errors apply `decisao:erro`, remove `decisao:pendente`, explain the failing field, and keep the issue open. A corrected issue can be edited and decided again.

Repository-write jobs use one concurrency group. Before pushing, the workflow updates from `origin/main`; a push conflict fails safely without closing the issue.

## Testing

Node's built-in test runner covers:

- parsing valid and malformed issue bodies;
- duplicate/missing headings and fenced payloads;
- path traversal and wrong-zone targets;
- accepted ficha rendering;
- rejected-state rendering;
- index row replacement/insertion;
- preservation of existing notes;
- repeated processing without duplicate state lines;
- refusal to overwrite an unrelated ficha.

A local dry-run generates payloads for all current fichas and verifies:

- 34 unique stable keys;
- 34 safe target paths;
- exactly one matching index row per target;
- no duplicate canonical ficha.

The workflow YAML is checked for syntax, required permissions, event filters, and concurrency settings before bulk issue creation.

## Rollout

1. Add tests and processor scripts.
2. Add the Issue Form and workflows.
3. Run all tests and a 34-ficha dry-run.
4. Create the four labels.
5. Create one pilot review issue and exercise both validation and a non-writing dry run.
6. Create the remaining review issues idempotently.
7. Confirm that every canonical ficha has exactly one open `decisao:pendente` issue.

Bulk creation occurs only after the implementation and dry-run checks pass.
